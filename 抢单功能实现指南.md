# 抢单功能实现指南

> 依赖：现有 RBAC 模块（角色 / 权限）、Redis、MyBatis-Plus
> 目标：一张工单只能被一个人抢到，并发下不超抢、不重复

---

## 一、表结构

```sql
USE nameless_db;

DROP TABLE IF EXISTS work_order;
CREATE TABLE work_order (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_no    VARCHAR(32)     NOT NULL COMMENT '工单号',
    title       VARCHAR(100)    NOT NULL,
    type        VARCHAR(30)     DEFAULT NULL COMMENT '类型：空调/水电/网络',
    content     VARCHAR(500)    DEFAULT NULL,
    status      VARCHAR(20)     NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/PROCESSING/COMPLETED/CANCELLED',
    assignee_id BIGINT UNSIGNED DEFAULT NULL COMMENT '处理人，NULL 表示未分配',
    grab_time   DATETIME        DEFAULT NULL COMMENT '抢单时间',
    deadline    DATETIME        DEFAULT NULL COMMENT '处理截止时间',
    version     INT             NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
    create_time DATETIME        DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME        DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted     TINYINT         DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_no (order_no),
    KEY idx_status_create (status, create_time),
    KEY idx_assignee (assignee_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='工单表';

DROP TABLE IF EXISTS grab_record;
CREATE TABLE grab_record (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_id    BIGINT UNSIGNED NOT NULL,
    user_id     BIGINT UNSIGNED NOT NULL,
    success     TINYINT         NOT NULL DEFAULT 1 COMMENT '1成功 0失败',
    cost_ms     INT             DEFAULT NULL COMMENT '抢单耗时，压测用',
    create_time DATETIME        DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_order_user (order_id, user_id),
    KEY idx_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='抢单流水（幂等 + 审计）';
```

**两个索引是重点**：
- `idx_status_create` 支撑「抢单池按状态筛选 + 时间排序」
- `uk_order_user` 是幂等的最后一道保险

## 二、状态机

```java
public enum OrderStatus {
    PENDING,      // 待抢
    PROCESSING,   // 已抢到，处理中
    COMPLETED,    // 已完成
    CANCELLED;    // 已取消

    /** 合法流转表 */
    private static final Map<OrderStatus, Set<OrderStatus>> ALLOWED = Map.of(
        PENDING,    EnumSet.of(PROCESSING, CANCELLED),
        PROCESSING, EnumSet.of(COMPLETED, PENDING),   // PENDING 用于放弃/超时释放
        COMPLETED,  EnumSet.noneOf(OrderStatus.class),
        CANCELLED,  EnumSet.noneOf(OrderStatus.class)
    );

    public boolean canTransferTo(OrderStatus target) {
        return ALLOWED.getOrDefault(this, Set.of()).contains(target);
    }
}
```

写这个枚举的意义：**所有状态变更都走 `canTransferTo` 校验**，防止出现「已完成的单又被抢」这类脏数据。面试时能讲「状态机约束」。

## 三、Mapper：并发控制就这一条 SQL

```java
public interface WorkOrderMapper extends BaseMapper<WorkOrder> {

    /**
     * 抢单：条件更新。
     * 返回 1 表示抢到，0 表示已被别人抢走 / 状态不对。
     * WHERE 里的 status 和 assignee_id 是并发控制的核心，不能省。
     */
    @Update("UPDATE work_order SET assignee_id = #{userId}, status = 'PROCESSING', "
          + "grab_time = NOW(), deadline = DATE_ADD(NOW(), INTERVAL 15 MINUTE), version = version + 1 "
          + "WHERE id = #{orderId} AND status = 'PENDING' AND assignee_id IS NULL AND deleted = 0")
    int grabOrder(@Param("orderId") Long orderId, @Param("userId") Long userId);

    /** 释放：只允许处理人自己放，或超时（grab_time 早于阈值）释放 */
    @Update("UPDATE work_order SET assignee_id = NULL, status = 'PENDING', "
          + "grab_time = NULL, deadline = NULL, version = version + 1 "
          + "WHERE id = #{orderId} AND status = 'PROCESSING' AND deleted = 0")
    int releaseOrder(@Param("orderId") Long orderId);

    /** 完成：必须是当前处理人 */
    @Update("UPDATE work_order SET status = 'COMPLETED', version = version + 1 "
          + "WHERE id = #{orderId} AND assignee_id = #{userId} AND status = 'PROCESSING'")
    int completeOrder(@Param("orderId") Long orderId, @Param("userId") Long userId);

    /** 超时未处理的单（定时任务用） */
    @Select("SELECT id FROM work_order WHERE status = 'PROCESSING' "
          + "AND deadline < NOW() AND deleted = 0 LIMIT #{limit}")
    List<Long> selectTimeoutOrders(@Param("limit") int limit);
}
```

## 四、Service 抢单主流程（核心）

顺序不能乱，每步都有理由：

```java
@Override
@Transactional(rollbackFor = Exception.class)
public Result grab(Long orderId, Long userId) {
    long start = System.currentTimeMillis();

    // ① 幂等前置：已经抢成功过 → 直接返回成功，不要报错
    //    用户双击、网络重试都会走到这里
    GrabRecord exist = grabRecordMapper.selectOne(
        new QueryWrapper<GrabRecord>().eq("order_id", orderId).eq("user_id", userId));
    if (exist != null && exist.getSuccess() == 1) {
        return Result.success("你已经抢到这一单了");
    }

    // ② 先查一次做友好提示（非并发安全，只为话术好看）
    WorkOrder order = this.getById(orderId);
    if (order == null) {
        return Result.error(400, "工单不存在");
    }
    if (!OrderStatus.PENDING.name().equals(order.getStatus())) {
        return Result.error(409, "手慢了，这单已经被抢走");
    }

    // ③ 真正的并发控制：条件更新，看影响行数
    int affected = this.baseMapper.grabOrder(orderId, userId);
    if (affected == 0) {
        return Result.error(409, "手慢了，这单已经被抢走");
    }

    // ④ 落流水（只在成功时写）
    GrabRecord record = new GrabRecord();
    record.setOrderId(orderId);
    record.setUserId(userId);
    record.setSuccess(1);
    record.setCostMs((int) (System.currentTimeMillis() - start));
    grabRecordMapper.insert(record);

    // ⑤ 投递超时任务（Redis ZSet，见第六节）
    long expireAt = System.currentTimeMillis() + 15 * 60 * 1000L;
    redisTemplate.opsForZSet().add(TIMEOUT_KEY, String.valueOf(orderId), expireAt);

    return Result.success("抢单成功");
}
```

**为什么 ① 在 ③ 前面**：幂等判断必须最先做，否则用户双击时第二个请求会因为「状态已变」收到「手慢了」，体验很怪。

**为什么 ④ 在 ③ 后面**：流水只记成功。如果先插流水再更新，CAS 失败时得回滚，逻辑更绕。

**为什么要 `@Transactional`**：③ 成功但 ④ 失败（比如唯一键冲突）时，要回滚 ③ 的更新，否则工单被占了却没流水。

## 五、幂等的三层设计

| 层次 | 手段 | 防什么 |
|---|---|---|
| 业务层 | ① 查 grab_record 直接返回成功 | 用户重复点击 |
| 数据库层 | `uk_order_user` 唯一索引 | 极端并发下两次插入 |
| 状态层 | `WHERE status='PENDING'` | 抢已被抢走的单 |

三层任意一层生效都不会出问题，这叫「纵深防御」。面试讲到这里基本够了。

## 六、超时释放：Redis ZSet

**不要用 `@Scheduled` 全表扫**（数据量一大就拖库），用 ZSet 当延时队列：

```java
private static final String TIMEOUT_KEY = "work:order:timeout";

// 抢单成功时写入（score 就是到期时间戳）
redisTemplate.opsForZSet().add(TIMEOUT_KEY, String.valueOf(orderId), expireAt);

// 每 30 秒捞一批到期的
@Scheduled(fixedDelay = 30_000)
public void releaseTimeoutOrders() {
    long now = System.currentTimeMillis();
    Set<String> due = redisTemplate.opsForZSet()
            .rangeByScore(TIMEOUT_KEY, 0, now, 0, 100);
    if (due == null || due.isEmpty()) return;

    for (String id : due) {
        WorkOrder order = this.getById(Long.valueOf(id));
        // 双重确认：可能用户已提交完成，或又被别人抢了
        if (order != null && OrderStatus.PROCESSING.name().equals(order.getStatus())) {
            this.baseMapper.releaseOrder(Long.valueOf(id));
            log.info("工单 {} 超时未处理，已释放回池", id);
        }
        redisTemplate.opsForZSet().remove(TIMEOUT_KEY, id);
    }
}
```

需要 `@EnableScheduling`（加在启动类或配置类上）。

**注意**：单机跑没问题；多实例部署时两个实例可能同时捞到同一单，靠 `releaseOrder` 的 `WHERE status='PROCESSING'` 保证只释放一次。这点也是可以讲的。

## 八、测试怎么写

### 1. 并发抢单测试（最值钱的一个）

```java
@Test
@DisplayName("100 个线程抢同一单，只能有一个成功")
void concurrentGrabOnlyOneWins() throws Exception {
    Long orderId = createTestOrder();          // 造一张 PENDING 单
    int threads = 100;
    ExecutorService pool = Executors.newFixedThreadPool(threads);
    CountDownLatch ready = new CountDownLatch(threads);
    CountDownLatch go = new CountDownLatch(1);
    AtomicInteger success = new AtomicInteger();

    for (int i = 0; i < threads; i++) {
        long userId = 1000 + i;
        pool.submit(() -> {
            try {
                ready.countDown();
                go.await();                     // 所有线程同时放行
                if (workOrderService.grab(orderId, userId).getSuccess()
                        && workOrderMapper.selectById(orderId).getAssigneeId() != null) {
                    success.incrementAndGet();
                }
            } catch (Exception ignored) {}
        });
    }
    ready.await();
    go.countDown();
    pool.shutdown();
    pool.awaitTermination(30, TimeUnit.SECONDS);

    assertEquals(1, success.get(), "只能有一个人抢到");
    assertEquals(1, grabRecordMapper.selectCount(
            new QueryWrapper<GrabRecord>().eq("order_id", orderId)), "流水只能有一条");
}
```

**注意**：这个测试不要加 `@Transactional`（否则并发线程看不到彼此的事务）。

## 九、最容易写错的五个点

1. **WHERE 里漏了 `status='PENDING'`** —— 整段逻辑就失效了，会超抢。这是唯一的并发控制点。
2. **用 `select` 判断再 `update`** —— 中间有时间窗，一百个线程都会通过 select。必须靠 update 的影响行数。
3. **加 `@Transactional` 但没配 `rollbackFor`** —— 默认只回滚 RuntimeException，稳妥写法是 `rollbackFor = Exception.class`。
4. **`grab_record` 没加唯一索引** —— 双击时可能插两条。
5. **超时任务用 `@Scheduled` 扫全表** —— 数据量上去会拖垮数据库，用 ZSet 或者加索引 + limit。

## 十、做完之后能讲什么

> 抢单用条件更新保证一单一人，`UPDATE ... WHERE status='PENDING'` 的影响行数就是判定结果；幂等做了三层：业务查重、唯一索引、状态条件。超时释放用 Redis ZSet 做延时队列，避免全表扫描。压测 [N] 并发抢 1 单，只有 1 个成功、流水只有 1 条。

把 `[N]` 换成你实测的数字，这段话就是简历里的一行。
